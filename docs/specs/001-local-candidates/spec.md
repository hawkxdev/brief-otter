# Single-source Local Collection

## Purpose and decision state

Help the owner review development opportunities from one Telegram channel in a local HTML report, without reading every source message manually. Project requests and job vacancies are both useful outcomes and must remain separate categories. A selected message is a candidate for human review, not a verified offer, accepted contract or application.

The [roadmap](../../ROADMAP.md#first-vertical-slice) owns the agreed first-slice direction: one manually started local collection, documented selection criteria, visible uncertainty and original links. The maintainer accepts D1/D2, the D3 storage policy and the [test execution policy](tasks.md#accepted-test-execution-policy), retaining the private pilot. The complete [D5 proposal](ai-classification.md) now specifies AI classification, a first candidate model and a local response contract. These are proposals for review, not an accepted model assignment or implemented behavior. The public baseline remains `f51ab4c21a4c0e4f4b5ee87adcf8612325494699`; the feature record owns progress and next actions.

The real source name, address, selection evidence and eventual configuration remain private. Public examples below are synthetic. A public checkout must be understandable without access to that private record and must require the user to supply their own approved source.

## User scenario

The owner selects an accessible source, an explicit reading interval and a topic profile. After one local command, they open a local HTML file, review project requests and vacancies separately, inspect uncertain messages and follow original links when more detail is needed. The report states which interval was requested, what was actually read and whether collection completed. The owner makes all decisions about responding or applying outside BriefOtter.

## Proposed requirements and acceptance

The accepted choices in D1/D2 and the D3 storage policy constrain this draft. Detailed behavior and acceptance cases below still require review and describe future observations, not checks already performed. The proposed [technical plan](plan.md) and [selection rules and Russian examples](rules.md) develop these IDs for review; neither document is an approved implementation assignment.

| ID | Required behavior | Acceptance observation |
|---|---|---|
| LC-01 | Run manually against exactly one explicitly configured channel, using the accepted first-run interval and timezone in D1. Resolve and record exact interval bounds at run start. Reject missing or invalid input before collection. | A valid interval selects only messages within its defined boundaries. Boundary timestamps and an invalid interval are covered. No implicit scan of other chats or all account history occurs. |
| LC-02 | Proposed implementation: analyse available text/captions with the per-message AI classifier in D5, with a locally validated response and code-owned disposition. The older rule algorithm remains a reference. Treat source text as data; no external job pages, comments, attachments, OCR or profile enrichment. | A linked description is not fetched. Missing terms/details are not invented. Semantic uncertainty is visible. Invalid replies and unattempted items are distinguished from valid model uncertainty and cannot become false exclusions. |
| LC-03 | Determine intent separately from topic relevance. Recognise `project_request`, `job_vacancy`, `executor_ad`, `resume`, `editorial` and `uncertain`. Ambiguous or conflicting intent remains uncertain. | The contrasting examples below have the expected outcomes. Shared Python keywords do not turn an executor advertisement or tutorial into a client request. An explicit project request and an explicit vacancy can both be selected. |
| LC-04 | Apply the accepted broad topic profile in D2 through documented, inspectable selection criteria. A language or framework alone must not become an eligibility gate. Keep intent, topic outcome and reasons distinct. Topic outcomes are match, no match or uncertain; unknown information must not be invented. | Contrasting technologies within the accepted directions can match. A change to the selection profile/rules/prompt is versioned and attributable. A clear topic mismatch is excluded. A plausible opportunity with undecidable topic relevance is available in the uncertain section. Salary, seniority and location remain unknown when absent. |
| LC-05 | Produce one self-contained local HTML report with separate project-request, vacancy and uncertain sections. Each displayed message has source display name, publication time with timezone, category, an available-text excerpt, decision reason and original message link. Show empty sections explicitly. | A synthetic report opens locally without a web server or automatic external requests. The owner can understand each displayed selection and follow its original link. Excluded messages are counted by disposition; totals reconcile with distinct messages analysed. |
| LC-06 | Identify a message by stable source identity plus message ID. Within a report, repeated delivery of that identity produces one entry. Each manual run builds a fresh report for its requested interval; it does not accumulate another copy in an inbox. | Delivering one message twice yields one entry. Two distinct message IDs remain distinct even when their text matches. Repeated local processing of the same input and substituted classifier reply is deterministic. Real-model stability is measured separately. No persistent processing cursor or unseen-only queue is implied. |
| LC-07 | Re-evaluate the currently available version of a message on a later run. A new report reflects only messages returned for that run; it does not claim to detect deletion or revoke older reports. Cross-posts and reposts with different identities remain separate. | Changing the text under the same identity changes its next classification without a second entry. An unavailable prior message is absent from the new report without being labelled as a confirmed deletion. Semantic cross-post grouping and real-time edit/delete tracking are excluded. |
| LC-08 | Make collection completeness and failures visible. Distinguish complete traversal of the accessible requested interval, partial collection, unavailable source and failed run. Record requested interval, obtained bounds when any, counts and a diagnostic reason without secrets. | An empty completed interval differs visibly from inaccessible history. An interrupted or capped traversal is partial, even if it found no candidates. 'Complete' describes the accessible traversal, not proof that every historical or deleted Telegram message was available. A failed run cannot leave an older report presented as its result. |
| LC-09 | Use only separately approved account access and a protected session carrier. Do not initiate interactive login, join a source, mark history read, send messages/reactions, change membership or substitute another account when collection fails. Respect platform-requested waits and stop on revoked or unusable authorization. | Synthetic access failures produce explicit failure states with no login prompt, join, outgoing action, immediate retry loop or account switch. An eventual opt-in live check verifies only the approved source and access path. Desktop visibility does not count as MTProto authorization. |
| LC-10 | Keep credentials, session material, source configuration and live reports outside the public repository. Persist only the data agreed under D3. Escape untrusted text in HTML and allow only the expected original-message link form. Do not execute message markup or embedded instructions. | Synthetic HTML/script content is rendered as text. A hostile link cannot become executable markup. Public fixtures and diagnostics contain no real channel identity, live message archive or secret. Report rendering makes no external calls. Model evaluation follows the accepted test policy and uses synthetic inputs; collected Telegram content requires its separate use/access approval. |

## Accepted local data handling

The maintainer accepts keeping one latest local HTML report, replaced by the next run or removed explicitly by the owner. Do not create a persistent message inbox, raw-message archive or report history for this slice. Keep fetched message content in memory during processing; persist only displayed candidates and uncertain items with the LC-05 fields and a limited available-text excerpt. Keep excluded-message counts and run diagnostics without their message bodies. The exact excerpt limit, output path and replacement behavior belong to the D5 technical plan.

The latest report remains until replacement or explicit removal; there is no fixed automatic expiry. Source configuration and live output remain private. The separate session carrier is governed by D4 and is not a message archive. No credential value belongs in a report, log, chat or public fixture.

Before live collection, resolve permitted content use against the [Telegram content terms](https://telegram.org/tos/content-licensing) and [API terms](https://core.telegram.org/api/terms). Local storage and deterministic filtering alone do not establish that the intended collection is permitted. The official [Telethon session documentation](https://docs.telethon.dev/en/stable/concepts/sessions.html) treats session material as account access; its carrier needs a separate protected location rather than the report directory. These prerequisites do not prevent preparation with synthetic inputs.

## Acceptance and limits

Technical acceptance requires evidence on the actual implementation revision for LC-01 through LC-10 and the agreed examples, including negative and failure cases. Then, under separately approved live access and data-use conditions, the maintainer reviews an agreed source sample and records correct selections, irrelevant selections and missed relevant opportunities. Assess requests and vacancies separately; mark a category absent from the live sample as not evaluated there. Do not invent an accuracy target before observing a baseline.

A source containing mainly vacancies can support the vacancy workflow but cannot alone demonstrate live project-request selection. Preserve contrasting synthetic cases for both categories and record this live evidence limit in the maintainer's usefulness decision. It does not add a second live source to this slice. A successful local report does not establish continuous monitoring, interruption recovery, sustained usefulness, complete Telegram coverage or account safety.

This slice excludes multiple sources, continuous monitoring, saved recovery cursors, notifications, outgoing Telegram actions, CRM or hiring-funnel integration, a web server, viewed/hidden state and semantic cross-post grouping. AI classification is an open D5 choice evaluated under the accepted test policy; model processing of collected Telegram content is not authorized by synthetic tests. Later milestones retain their own decisions. Commit, publication and implementation approval remain separate from specification review.
